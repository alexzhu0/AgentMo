## Summary

The official OpenClaw installation documentation currently states Node 22.19+, Node 23.11+, or Node 24+, which is equivalent to the locked AgentMo target range `>=22.19.0 <23 || >=23.11.0`. [CITED: https://docs.openclaw.ai/install/node] The latest official release is `v2026.6.11`, released on 2026-06-30. [CITED: https://github.com/openclaw/openclaw/releases/tag/v2026.6.11] Its package manifest declares the broader npm installation floor `engines.node: ">=22.19.0"`; this declaration must be recorded separately from the narrower official supported-runtime documentation rather than silently treating the two as identical. [CITED: https://github.com/openclaw/openclaw/blob/v2026.6.11/package.json]

Repository inspection found five production mutation paths: OpenClaw scaffold materialization, live run, live replay, shell `agents add`, and shell gateway start. They converge on three lowest enforcement seams: `scaffoldAgent` before target-file writes, `runRuntimeCommand` before child spawn (with earlier run/replay checks before output preflight), and the shell helper before its first `mktemp`, scaffold, or direct OpenClaw invocation. [VERIFIED: repository inspection] `run-plan`, reports, evals, and observation remain non-mutating planning/evidence paths and must not be needlessly blocked. [VERIFIED: repository inspection]

The current host has Node `v24.18.0`, but no Node 20 runtime manager, Docker, OpenClaw binary, or repository CI workflow was found. [VERIFIED: local environment probe] Therefore the plan must add a real Node 20 execution lane and keep it `untested` until that lane actually runs. Node 20 itself reached EOL on 2026-03-24, so the lane is compatibility evidence only, not a recommended production runtime. [CITED: https://nodejs.org/en/about/previous-releases]

**Primary recommendation:** Implement one immutable runtime contract sourced directly from `process.versions.node`, enforce it at the three lowest seams, prove the five mutation paths fail with zero side effects under a real Node 20 process, and generate a release matrix that distinguishes upstream declaration, official support, contract-tested versions, target-executed versions, and untested rows.

### Pattern 1: Non-injectable current-process assertion

The production assertion accepts no version, provider, callback, or options object. It reads the current runtime directly; a separate pure predicate may accept a version string for boundary-table tests, but it is not a mutation authorization API.

```js
export const OPENCLAW_TARGET_NODE_RANGE = ">=22.19.0 <23 || >=23.11.0";

export function assertCurrentOpenClawTargetRuntime() {
  const observation = observeCurrentRuntime(); // reads process.versions.node directly
  if (!observation.openClawTargetSupported) {
    const error = new Error("OpenClaw target runtime is unsupported.");
    error.code = "AGENTMO_OPENCLAW_RUNTIME_UNSUPPORTED";
    throw error;
  }
  return observation;
}
```

### Pattern 2: Defense-in-depth ordering

- `scaffoldAgent`: resolve the selected target, assert when it is `openclaw`, then build state/preflight/write. [VERIFIED: current write order in `src/scaffold.js`]
- `executeRuntimeRun` and `replayRunState`: for `live === true`, assert before runtime-env resolution, run-index preflight, runner selection, or output writes; `runRuntimeCommand` repeats the assertion immediately before `spawn`. [VERIFIED: current order in `src/run-state.js` and `src/runtime-execution.js`]
- `openclaw-live-smoke.sh`: invoke the same CLI check after argument validation but before env-file value reads, `mktemp`, scaffold, state-file redirection, `agents add`, or gateway start. [VERIFIED: current order in `scripts/openclaw-live-smoke.sh`]

### Pattern 3: Evidence taxonomy, not a boolean matrix

Each compatibility row should carry: `component`, `declaredRange`, `upstreamSource`, `runtimeVersion`, `lane`, `commandSet`, `status` (`tested`, `failed`, `untested`), `observedAt`, `evidenceRef`, and `remainingRisk`. A target contract test is not a target live execution; neither is domain quality or production approval.

### Anti-Patterns to Avoid

- Accepting `version`, `versionProvider`, `processVersion`, or an env override in a production mutation API.
- Checking only in CLI dispatch; direct imports and shell OpenClaw commands would bypass it.
- Checking only inside `runRuntimeCommand`; scaffold writes and run/replay output preflight occur outside that seam.
- Treating `package.json#engines`, a mocked version, or a release table as actual Node 20 execution evidence.
- Letting the shell create temporary state before the gate and calling cleanup “zero side effects.”
- Updating maintained docs while leaving generated runbooks or verification hints with ungated direct mutation commands.
- Marking `v23.0.0` supported because npm `engines.node` says `>=22.19.0`; official OpenClaw docs explicitly exclude Node 23 builds before `23.11.0`. [CITED: https://docs.openclaw.ai/install/node]

## Common Pitfalls

### Pitfall 1: Gate after preflight that already mutates
**What goes wrong:** a rejected target leaves an output directory, lock, state directory, or redirected file.
**How to avoid:** record side-effect spies for mkdir/open/write/rename/unlink/spawn and assert the list is empty on each incompatible path.

### Pitfall 2: Node 20 full-suite ambiguity
**What goes wrong:** OpenClaw success tests legitimately cannot run on Node 20 after the gate is correct, so a vague “run all tests” lane either fails or skips the target boundary.
**How to avoid:** define an explicit `check:core:node20` lane that runs syntax/core contracts plus the incompatible-target negative matrix; keep target-success suites in supported Node lanes. The command list must be recorded in the release matrix.

### Pitfall 3: Declaration/observation conflation
**What goes wrong:** `engines.node`, official docs, unit range tables, local Node 24 execution, and live OpenClaw execution are collapsed into “supported.”
**How to avoid:** separate `upstream-declared`, `official-supported`, `contract-tested`, `core-executed`, and `target-executed` fields/rows.

### Pitfall 4: Stale generated guidance
**What goes wrong:** source and CLI are gated but a freshly generated runbook still tells an operator to mutate OpenClaw directly.
**How to avoid:** generate range/preflight wording from the production constant and scan all maintained/generated command surfaces in one test.
