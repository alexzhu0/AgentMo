# 2026.07.10 — Stage 2 design-plan contract

## 背景

AgentMo 的业务模型明确拆成三个阶段：

1. 搜索/收集数据并形成 discovery database。
2. 根据用户需求结合数据库规划新 Agent。
3. 完成 Agent 设计、实现和交付证据闭环。

前一轮 Stage 1 和 Stage 3 已经有较完整的 artifact contract，但 Stage 2 仍主要通过 `blueprint-draft` 隐式完成规划。本次把 Stage 2 独立成可审计的 `agentmo.design-plan.v1`。

## 架构决策

采用：

- Stage 2 先生成 `agentmo.design-plan.v1`，再把通过验证的 design-plan 作为 blueprint draft 的可选但推荐输入。
- `design-plan` 记录 requirements trace、evidence map、gaps、architecture plan、tool contract plan、eval plan、evidence policy、governance gates 和 certification boundary。
- `source_refs` 由共享 helper 统一验证，避免 `need-report`、`design-plan`、`blueprint-draft` 三处漂移。
- `blueprint-draft --design-plan` 只记录 bounded provenance 和摘要，不复制完整 evidence map。
- 新协作者入口集中到 `CONTRIBUTING.md`，本地 agent 操作规则集中到 `AGENTS.md`，session handoff 集中到 `docs/OMX_SESSION_MIGRATION.md`。

拒绝：

- 只增强 `blueprint-draft`：会继续隐藏 Stage 2 规划过程。
- 立即构建交互式 planner：当前更需要稳定 artifact contract。
- 强制所有旧 `blueprint-draft` 调用立刻迁移：旧 DB+need 路径仍保持兼容。

## 非认证边界

- `agentmo.design-plan.v1` 是规划合同，不是 runtime execution 证据。
- `design-plan` 不认证 domain-wide quality、OpenClaw runtime parity、production deployment 或 customer approval。
- Missing/partial evidence 只能作为显式 gap/eval/governance constraint，不能升级成生产声明。

## 后续风险

- 当前 evidence matching 是 deterministic lexical heuristic；后续可升级语义匹配，但不能破坏 Stage 1/2/3 artifact 解耦。
- GitHub Release 尚未由本地实现自动发布；发布/tag 需要单独执行并记录。
